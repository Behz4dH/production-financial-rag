● Happy to. Here's the honest tradeoff for this specific project — a
  batch-ingested docs Q&A RAG.

  What actually separates them isn't "local vs cloud" — it's where the index 
  lives relative to your app.

  Persistent Chroma — the index is a directory on the same machine/container as
  the API.
  - ✅ Zero infra, zero network hop per query (fastest retrieval), no account,
  no connection string, no migrations.
  - ✅ Perfect fit for "batch-ingest a folder → serve queries." Survives
  restarts.
  - ✅ "Production" is fine at single-node scale.
  - ❌ The index is tied to that node's disk. Multiple app instances behind a
  load balancer can't cleanly share one writable index. No managed backups/HA —
  you back up the directory yourself.

  Supabase pgvector — the index is a managed Postgres in the cloud; your app
  connects over the network.
  - ✅ Stateless app: run 1 or 10 instances, all share one index. Managed
  backups, HA, a dashboard.
  - ✅ SQL metadata filtering, and you can co-locate relational data (users, doc
  metadata) next to vectors.
  - ❌ Network latency on every retrieval, a Supabase account + connection
  string to manage, and you own the schema/migration story. Costs scale with
  data beyond the free tier.
  - ❌ At small scale it's more moving parts for no answer-quality gain.

  The deciding question is one thing: will you run more than one app instance 
  sharing the same index, or do you need managed backups/HA now?
  - If no (single service, you control the disk/volume) → persistent Chroma is
  genuinely the better engineering choice. Simpler, faster, less to break.
  - If yes (horizontal scaling, shared index, managed durability) → Supabase 
  pgvector earns its complexity.

  My recommendation: Since we already agreed on an abstracted vector-store
  layer, start with persistent Chroma behind a VectorStore interface, and I'll
  include a documented pgvector adapter as the drop-in scale-up path. You get
  simplicity now and a config-swap (not a rewrite) later — you don't have to bet
  the architecture on this today.

  One thing that tips it: how you'll deploy.

  rag/retrieval/ — The retrieval brain.

  - hybrid.py: BM25 + vector ensemble (weighted).

  2. Data flow

  Ingestion (offline, python -m rag.ingestion or a make ingest):
  data/docs/* → load → chunk (+metadata) → embed (local HF) → persist Chroma at
  data/chroma/. Prints a summary (files, chunks, dims). Also builds/persists the
  BM25 corpus.

  Query (online, per request):
  POST /chat {message, thread_id, mode?}
   → rate-limit → sanitize input → cache lookup (hit ⇒ return)
   → retriever(mode):
       hybrid:  BM25 ⊕ vector → rerank(top_k→top_n)
       agentic: LangGraph(retrieve→grade→[rewrite→retry ≤N]→generate|fallback)
   → generation: grounded prompt + cited context → LLM
   → validate/mask output → cache set → metrics update
   → 200 {response, citations[], model_used, mode, cached, latency_ms}
  LangSmith tracing wraps retrieval + generation when a key is present (no-op
  otherwise).

  3. Config & env (the "clean env validation" you asked for)

  Single Settings(BaseSettings) — typed, .env-loaded, @lru_cache singleton,

  4. API surface

  POST /chat (query), GET /health (liveness), GET /metrics (requests, error

  the React dev origin.

  5. Error handling & production concerns

  Global exception handler → structured ErrorResponse (never a raw 500).
  Provider timeouts → retry (max_retries) then primary→fallback model.
  Empty/low-relevance retrieval → explicit "not in my knowledge base" (not a

  - 20 SEC 10-K / annual-report PDFs (real companies: TransUnion, Petra
  Diamonds, Mitsui O.S.K. Lines, etc.).
  - 40 questions with a golden, categorized answer key — tagged hallucination,
  tricky, compare, retrieval.

  And it's deliberately adversarial. Look at the answer distribution:
  - ~60% of correct answers are "N/A" — because the company isn't in the corpus,
  or the report is for 2022 but the question asks about 2023. These test
  refusal / hallucination-resistance, not retrieval.
  - tricky = compute a financial ratio (Net Profit Margin, ROA, Quick Ratio,
  Operating Margin, FCF = OCF − capex) from underlying line items → numerical 
  reasoning, not lookup.
  - compare = "which company had higher X" across multiple docs, in different 
  currencies (yen vs CHF vs USD) → multi-doc retrieval + reasoning.
  - retrieval = answer on specific pages, sometimes multiple valid values.

  Why this is actually a gift (and a fork in the design)

  For an AI/ML eng interview this is far stronger than a toy corpus — it maps
  almost 1:1 onto the course's failure modes, and the headline becomes: "On an 
  adversarial financial benchmark, my system correctly refuses X% of 
  unanswerable questions and grounds every answer with page citations."
  Refusal-under-pressure is exactly what senior reviewers probe.

  But it forces three design changes I need your call on, because two of them
  can expand scope:

  1. Grounding/refusal becomes the primary engineered goal (not a fallback). The
  agentic grade→refuse path and strict "answer only from context, else N/A" is
  now the centerpiece. ✅ No scope risk — we planned this.
  2. Tables. 10-K financials are table-heavy, and pypdf mangles tables badly
  (the course's "Multimodal RAG" failure mode). Getting numbers right likely
  needs table-aware extraction (e.g., pdfplumber). This is added ingestion work.
  3. Numerical reasoning. tricky questions need the LLM (or a tool) to compute
  ratios from retrieved line items. That's a generation/agent concern beyond
  retrieval.
